# RedSentinel 面试问答指南

回答结构统一为：

```text
结论 -> 设计理由 -> 代码/实验依据 -> 局限 -> 下一步
```

## 1. 为什么普通 LLM 安全评测不能直接用于 Agent？

结论：Agent 风险不仅存在于最终文本，还存在于检索内容、工具参数、记忆写入和外部状态变化。

依据：

- `Trajectory` 同时记录 LLM、tool、memory、state 和 guard decision；
- evaluator 对逐步轨迹做判断，而不只检查 answer；
- tool tampering、memory poisoning 和 goal drift 可能没有明显危险输出。

局限：统一 trajectory 仍依赖 adapter 正确采集；采集遗漏会形成可观测性盲区。

## 2. 攻击成功如何判定？Oracle 会不会误判？

结论：攻击成功应由场景级 success criteria、实际副作用和策略违规共同判定，不能只靠关键词。

设计：

- 确定性规则处理明确策略；
- 异常模型处理工具序列和参数偏移；
- 语义探针处理难以枚举的意图；
- 节点归因保留证据；
- `ask`、拒答、timeout 和 runtime error 分开记录。

局限：Oracle 仍可能与攻击生成器共享偏差，因此正式实验需要 holdout、人工抽样和 evaluator ablation。

## 3. 如何避免进化过程对 evaluator 过拟合？

措施：

- development 和 holdout 按 payload 来源组隔离；
- holdout 不参与规则、阈值和候选选择；
- 增加未知攻击和第二个 Agent；
- 比较规则、异常、语义探针的消融；
- 统计重复候选率和攻击多样性；
- 最终结果由多 seed 和人工抽样复核。

当前状态：数据分组和 manifest 已有，真实多 Agent holdout 实验属于 P1。

## 4. 为什么双边进化可能优于单边优化？

攻击侧持续发现当前防御的薄弱点，防御侧针对具体节点修复；单边攻击进化无法降低风险，单边防御容易针对固定攻击集过拟合。

但双边进化并不天然更优，必须控制：

- 相同数据；
- 相同查询和执行预算；
- 相同 seed；
- 相同停止条件；
- 相同 evaluator。

项目提供固定、仅攻击、仅防御、双边四类 arm，但真实效果结论仍待 P1/P2。

## 5. 如何测量 FPR、业务 utility 和成本？

- FPR：benign/control case 被错误 block/ask 的比例；
- business success：正常任务是否完成，而不是仅看是否 allow；
- latency：wall-clock 和分阶段耗时；
- model cost：请求数、输入/输出 token 和货币成本；
- runtime cost：工具调用、容器执行和重试；
- human cost：ask 次数和等待时间。

不能把低 ASR 单独视为优秀防御，因为“全部拒绝”也可能得到低 ASR。

## 6. 合成 Agent 与真实 Agent 的差距是什么？

合成环境适合：

- 确定性回归；
- 检查指标和证据链；
- 低成本消融；
- 重现边界条件。

它不能证明：

- 真实模型遵循相同分布；
- 工具规划和长程状态变化一致；
- 方法可跨框架泛化；
- 实际 token、延迟和成本可接受。

因此离线结果属于工程和方法 smoke，真实结论需要 OpenManus 和第二个 Agent。

## 7. 哈希链能解决什么，不能解决什么？

能检测：

- 已记录事件被修改；
- 中间事件被删除；
- 顺序被改变；
- 不同 artifact 版本不一致。

不能解决：

- 数据在写入前就是伪造的；
- 根密钥或宿主机完全失陷；
- 攻击者重放一整套旧的有效证据；
- 时间戳没有可信时间源；
- 日志未被采集。

要进一步增强，需要签名、可信时间、远端锚定、密钥轮换和独立验证者。

## 8. 哪些是个人实现，哪些是第三方？

个人重点：

- 研究契约和模块边界；
- 协同进化状态机；
- 基线和消融；
- 指标及失败归因；
- provenance/evidence；
- 数据治理和自动化测试；
- Product API 与研究核心解耦。

第三方：

- OpenManus 是被测开源 Agent；
- LangGraph/FastAPI/Pydantic 是基础框架；
- Isolation Forest 是标准异常算法；
- 公开 taxonomy 和数据集是研究输入。

## 9. 当前最薄弱的证据是什么？

跨 Agent 和多模型实验仍然不足。当前最可靠的是 778 项默认全量测试、结构化证据链、
deterministic smoke 和 OpenManus W2 单 Agent 门禁，不能据此得出跨 Agent 或论文
显著性结论。

改进顺序：

1. 真实 OpenManus；
2. 第二个 Agent；
3. 两个模型家族；
4. 3-seed pilot；
5. 5–10 seed formal。

## 10. 如果重做一次，会删掉什么？

- 更早把 Product API 降为展示层；
- 不以比赛阶段编号组织长期代码；
- 不同时扩展过多攻击报告和页面；
- 更早冻结 ExperimentManifest 和数据划分；
- 先完成两个真实 Agent，再扩展更多演示功能。

## 11. 为什么使用 AgentProfile？

它提供结构化先验：

- 节点和工具；
- 权限与数据边界；
- RAG 和记忆能力；
- 暴露风险面；
- 证据来源。

没有 profile 时只能使用通用攻击；有 profile 可以减少无效候选。但 LLM 画像只作为候选，不能覆盖无证据事实。

## 12. 协同进化算法目前有多强？

当前已完成工程状态机、种群、精英保留、探索选择、停止条件、ledger 和基线框架。尚未完成正式 Pareto selection、复杂度分析和真实多 seed 显著性，因此应描述为“实验性协同进化框架”，而不是成熟新算法。

## 13. 为什么不直接使用 LLM-as-a-Judge？

单一 Judge：

- 可能受攻击文本影响；
- 成本和延迟高；
- 输出不稳定；
- 归因弱；
- 与攻击生成模型可能共享偏差。

因此项目使用规则、结构信号、异常检测和可选语义探针的组合，并保留输入证据。

## 14. 项目与现有实习的最大连接点是什么？

连接点不是业务领域，而是评测方法：

- 建立可定义的质量/安全标准；
- 构造稳定测试集；
- 自动执行和比较；
- 精准归因失败；
- 生成可验证报告；
- 用反馈推动系统迭代。

区别是 Agent 安全把被测对象扩展到了动态执行和外部副作用。

## 15. 项目如何体现工程能力？

- 多包迁移为统一领域架构；
- 旧 API 兼容和回归；
- 778 项默认全量测试；
- 统一 CLI；
- 数据 hash 和 provenance；
- adapter 与核心解耦；
- Product API 领域服务拆分；
- 无网络默认测试和环境分层。

## 16. 项目如何体现研究能力？

- 明确 RQ 和假设；
- 公平基线；
- 消融；
- development/holdout；
- 多 seed 统计；
- 效应量和置信区间；
- Go/No-Go；
- 有效性威胁；
- 不把 smoke 当论文结论。

## 17. 常见追问准备

### 系统设计

- adapter 如何保证轨迹字段一致？
- sandbox 的隔离边界是什么？
- 如何处理长轨迹和大日志？
- 多租户为什么不是核心研究问题？

### 算法

- candidate 如何编码？
- fitness 如何定义？
- exploration rate 如何选择？
- 如何避免候选坍缩？
- 停止条件如何影响结果？

### 实验

- 为什么选择这些攻击类别？
- success criteria 谁定义？
- holdout 如何构造？
- 样本量和统计功效如何确定？
- 模型升级后如何复现？

### 密码学与可信性

- 哈希链与签名的差别？
- 根信任在哪里？
- 如何处理密钥泄漏和轮换？
- 如何防重放？
- 什么条件下可以给出形式化安全性质？
